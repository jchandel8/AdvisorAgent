The 30-second pitch

"AdvisorAgent is a wealth-management app where financial advisors ask questions in plain English, like which of my clients are overweight in tech and have a review due this month, and a Claude-powered agent answers by calling read-only tools over portfolio data. There are three portals: advisor, client and admin. The point of the project is security: the AI can only ever see the accounts the signed-in advisor is allowed to see, and that is enforced in the database query, not in the prompt."

The one security rule. Who you are comes only from the verified login token (Cognito), never from the prompt, the model or the browser. Every tool gets advisor_id from the backend, and every query joins through the account_access table. The model never writes SQL.

Layer by layer

In build order. Each part has what it is, why it's that way, and the line to say.

Step 1 · Database

Postgres schema with an access list at the centre

Accounts are the central entity. Holdings, transactions, performance and documents all belong to an account. The account_access table links one account to one person with a role (owner, joint owner, advisor, viewer). It has two real foreign keys, advisor_id and client_id, and CHECK constraints so exactly one is filled and the role fits the person type.

Why: the database itself refuses a bad permission row. Values like market value and gains are computed in SQL, never stored, so they can't go stale. Plain SQL with psycopg (no ORM) keeps the access join visible.

Say it"Permissions are data, not code. One table decides who sees what, and constraints stop invalid rows from ever existing."
Step 1 · Data

A deterministic mock-data generator

Faker with seed 42 makes 10 advisors, 200 clients and 348 accounts (15% joint, about 10% with two advisors). Holdings aren't random: they come from replaying two years of simulated transactions against a price path, so holdings, cost basis, gains and returns all agree. Some clients are deliberately tech-heavy so the demo question has a real answer.

Say it"Same seed, same data every run, so tests and demos are repeatable. And the numbers reconcile, because holdings are derived from transactions."
Step 1 · Security core

One access layer every query uses

A single SQL fragment, VISIBLE, lists the accounts the current person can see. Every tool and every portal endpoint starts from it. If an advisor shares one account with a client, they see that client but only that shared account. Asking for an account you can't see returns the same "not found" as an account that doesn't exist, so IDs can't be probed.

Say it"There's exactly one place access is decided. A test runs every tool as an advisor with no access, so a new tool that forgets the join fails automatically."
Step 1 · AI agent

Six tools and a manual tool-use loop

Tools: get_my_clients, get_accounts, get_holdings, get_transactions, get_performance, find_reviews_due. Their schemas sent to Claude don't contain advisor_id at all. The model's input is validated with Pydantic set to forbid extra fields, so a model that tries to pass advisor_id is rejected. The backend then calls the tool with the signed-in advisor's ID. Tools run in read-only transactions and do the math in SQL. The loop runs up to 10 rounds with Claude Sonnet 5.5.

Why a manual loop: every step is readable code, which makes it easy to add checks between steps and easy to explain.

Say it"Even if the model is tricked by a prompt injection, the worst it can do is ask for data this advisor is already allowed to see."
Added after testing · Guardrails

Keeping the assistant on task and honest

  • Scope check: Claude Haiku 5.5 classifies each question first (in scope, off topic, manipulation). If the check fails, the question is blocked. This was added after "what's the diameter of the moon?" got an answer.
  • Facts only: the prompt forbids buy or sell recommendations.
  • Selected client is a hard scope: picking a client in the chat dropdown filters the access layer itself, so other clients can't leak in.
  • Answer check: if the answer quotes figures but no tool was called, it's replaced and removed from history.
  • Limits: 10 a minute, 100 a day per advisor, with an audit row for every request.
  • Answer cache: repeat questions are free. The key includes a fingerprint of the advisor's permissions, so a grant or revoke automatically stops old answers being served.
Say it"Defence in depth: a cheap classifier in front, data-level scoping in the middle, a fabrication check at the end, and cost limits around all of it."
Step 2 · Backend and frontend

FastAPI and one Angular app with three portals

One FastAPI service serves the client, advisor and admin endpoints plus the assistant. The Angular app (signals, standalone components, Tailwind, ECharts) has /advisor, /client and /admin. The backend checks role and access on every call; the frontend hiding a page is only convenience. Locally, docker compose up starts Postgres, API and web together.

Say it"The UI is untrusted. You can open the advisor portal and the client portal side by side and see the same account from both sides."
Step 3 · Login

Amazon Cognito with three groups

The user pool has groups advisors, clients and admins. The frontend uses the authorization code flow with PKCE (the standard flow for browser apps; no secret in the browser). The backend verifies the access token itself: signature against Cognito's public keys (JWKS), issuer, expiry, token type, app client ID, and exactly one group. The Cognito username matches the database username. A local "demo picker" mode exists for development and refuses to start on AWS.

Playwright browser tests log in and check what each role can see.

Say it"Passwords never touch my app or database. Cognito handles them; I only verify a signed token."
Step 4 · Admin

Admin portal, audit log, reset

Admins create users (database row and Cognito login together), create accounts, and grant or revoke access. Each change and its permission_audit row are written in the same transaction, so there's never a change without a record. Rules prevent leaving an account with no owner or no advisor. Admins manage access but don't read portfolios. A reset script restores the seeded data for demos.

Say it"Audit and change are atomic: if the audit insert fails, the grant rolls back."
Step 5 · Packaging

One production container

A multi-stage Dockerfile: stage one builds Angular, stage two is Python with the built files copied in, so FastAPI serves the website and the API from one container. On start, start.sh runs migrations, seeds data only if the database is empty, creates the Cognito demo logins, then starts the server.

Say it"One image, one service, no separate web hosting. A fresh deploy comes up already seeded and demo-ready."

The Terraform, file by file

Terraform describes AWS resources as code; plan shows what would change, apply makes it so, and a state file remembers what exists. The code is split into three stacks because the parts have different lifetimes.

StackWhat it createsLifetime / status
infra/bootstrap S3 bucket for the app stack's state file; GitHub OIDC identity provider; IAM role advisoragent-github-deploy that only the repo's main branch can assume. Once. Not applied.
infra/persistent Cognito pool, app client, hosted login domain and 3 groups. ECR image registry (with a rule that keeps only recent images). Two Secrets Manager entries: Anthropic API key and demo password (values typed in by you, never in code). Kept forever. Cognito applied; ECR and secrets not applied.
infra/app RDS Postgres 17 (db.t4g.micro, private, encrypted, password managed by RDS); security group allowing port 5432 only from inside the VPC; ECS cluster; ECS Express Mode service (0.5 vCPU, 1 GB, port 8000, health check /api/health); three IAM roles; CloudWatch log group. Output: APP_URL. Disposable: Deploy creates it, Teardown destroys it. Not applied.
Why three stacks instead of one?

Bootstrap exists because of a chicken-and-egg problem: the S3 bucket that stores Terraform state can't store its own state, so it's created separately with local state.

Persistent holds things that are slow or painful to recreate: Cognito users, the image registry and the secrets (deleted secrets keep their name reserved for days, so recreating them fails).

App holds everything that costs money by the hour. Destroying only this stack takes the bill from about $60–90 a month to about $1–3.

What are the three IAM roles in the app stack?

Execution role: used by ECS to start the container: pull the image from ECR, read the secrets, write logs.

Task role: what the running app itself may do: only the Cognito admin calls needed to create users.

Infrastructure role: lets Express Mode create and manage the load balancer, certificate and scaling on your behalf (AWS-managed policy).

Separating them is least privilege: the app code can't, for example, read secrets it wasn't given.

How does the app get the database password?

RDS creates and rotates the master password itself and stores it in Secrets Manager (manage_master_user_password). ECS injects just the password field into the container as DB_PASSWORD. config.py assembles the connection string from DB_HOST, DB_USER, DB_PASSWORD with sslmode=require. The password is never in code, Terraform files or GitHub.

What is ECS Express Mode and why use it?

A newer, simpler way to run a container on ECS Fargate: you give it an image, a port and a health check, and it creates the load balancer, HTTPS URL, target group and scaling for you. Fargate means no servers to manage. It replaces a lot of hand-written load balancer Terraform.

Why the default VPC and no NAT Gateway?

A NAT Gateway costs about $33 a month even when idle, more than the rest of the demo. Tasks in the default VPC's public subnets get a public IP so they can reach the Anthropic API, ECR and Secrets Manager directly. The database stays private: not publicly accessible, and its security group only accepts traffic from inside the VPC. In production you'd use private subnets with NAT or VPC endpoints. This is the one part not yet proven on AWS.

How is Terraform run?

infra/tf.sh runs a pinned Terraform version (1.17.2) inside Docker, so nothing has to be installed and everyone uses the same version. Provider versions are locked in .terraform.lock.hcl. All three stacks pass terraform validate; plans show 7 resources for bootstrap and 4 new ones for persistent.

The deploy flow (GitHub Actions)

  1. CI (ci.yml, every push): lint with ruff, run the backend tests against a real Postgres service, run the frontend tests and build.
  2. Deploy (deploy.yml, button): GitHub proves its identity to AWS with an OIDC token and gets short-lived credentials for the deploy role. No AWS keys are stored in GitHub. It builds the image, pushes it to ECR, runs terraform apply on the app stack, and prints the URL.
  3. Teardown (teardown.yml, button): you must type DESTROY; it destroys only the app stack.
Say it"Keyless deploys: GitHub's OIDC token is trusted only for my repo's main branch, and the credentials expire after the job."

Questions to practise

What stops a prompt injection from reading another advisor's data?

The model never controls identity. advisor_id isn't in any tool schema, model input that includes it is rejected, and the backend injects the ID from the verified token. Every query filters through account_access. So injection can change which allowed data is requested, never which data is allowed.

Why not let the model write SQL? It would be more flexible.

Generated SQL can't be reliably checked for the access join, and one missed WHERE clause leaks everything. Fixed tools with typed inputs are testable, and each does its math in SQL so the model can't miscalculate totals.

How do you know the access rules work?

A small hand-built test fixture where the right answer is known: an advisor who shares one of a client's accounts sees only that account; an advisor with no access sees nothing from any tool; a closed account disappears. A parametrised test runs every registered tool as the no-access advisor, so new tools are covered automatically.

How do you control AI cost on a public demo?

Haiku (cheap) screens questions before Sonnet runs; per-advisor limits of 10 a minute and 100 a day; an answer cache so repeats cost nothing; prompt caching on the system prompt and tools; and the whole stack can be torn down between demos.

What happens when an admin grants access?

One transaction inserts the account_access row and the audit row. On the advisor's next page load the access layer includes the account, and the agent can answer about it. The cache key includes a permissions fingerprint, so no stale cached answer survives the change.

Why Cognito instead of your own login?

No passwords stored anywhere I own; MFA, lockout and password reset come built in; groups map directly to roles. The backend verifies tokens itself with the public keys rather than trusting the frontend.

What would you change for real production?

Private subnets with VPC endpoints or NAT; narrow the deploy role from admin to the exact permissions; Multi-AZ RDS with backups and a final snapshot; two or more tasks; Bedrock instead of the Anthropic API so data stays in the AWS account; tracing and alerts (planned in step 6); tighter guardrail evals.

What was the hardest bug?

Two good ones. Selecting a client in the chat still let the model answer about other clients, so the selection became a filter inside the access layer rather than a prompt hint. And the answer cache expired entries instantly once the pinned data date was in the past; found by a failing test, fixed by using the real clock for expiry.

Be honest about what isn't done

  • Nothing from step 5 is on AWS yet; only the Cognito pool exists. Plans have been checked, not applied.
  • Internet access from the default VPC without NAT is expected to work but unproven.
  • The deploy role has AdministratorAccess for now; it should be narrowed after the first deploy.
  • Step 6 not started: MCP server for the tools, document search (Postgres full-text through the access layer), tracing with CloudWatch and X-Ray, more evals.

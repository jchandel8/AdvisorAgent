    Who can do what: IAM

    Every AWS call is checked by IAM (Identity and Access Management), and anything no policy allows is denied. This project has no stored AWS keys anywhere: each part of the system assumes a role and receives temporary keys that expire within an hour.

    Principal

    Who is making the call: a person, a GitHub workflow, a running container or an AWS service acting for you.

    Role

    An identity with permissions but no password. Something trusted assumes it and gets temporary keys from STS (the Security Token Service).

    Trust policy

    Attached to the role: who may assume it. For the deploy role, only GitHub tokens for this repo's demo environment.

    Permission policy

    What the role may do: actions on resources, e.g. secretsmanager:GetSecretValue on 2 named secrets only. Deny is the default; an explicit deny always wins.

    How a deploy gets keys

    1. GitHub issues the job a signed token: repo jchandel8/AdvisorAgent, environment demo.
    2. STS checks it against the deploy role's trust policy (audience sts.amazonaws.com, subject with the repo's permanent IDs).
    3. It returns keys that expire within an hour. Nothing is left to leak afterwards.

    How the running app gets keys

    ECS gives the container the task role's temporary keys through a local credentials endpoint, and boto3 finds them automatically. They rotate on their own. The code never holds an AWS key, and the image contains none.

    Two roles for one container

    The execution role is used only before your code starts: pulling the image and injecting secrets. The task role is what your code can do. So at runtime the app can't call Secrets Manager or ECR; it only has the values it was given at start.

    IAM vs Cognito

    IAM: which AWS identities (GitHub, ECS, the app) may use which AWS resources. Cognito: your app's users (advisors, clients, admins) signing in. Then the app's own account_access table decides which accounts each user sees. Three layers, three jobs.

    Least privilege, honestly

    App roles are scoped to named resources (3 secret ARNs, one user pool ARN). The deploy role is the exception: Terraform creates many resource types, so it has admin rights, fenced by the trust policy and 1-hour sessions. Narrowing it is on the to-do list.

    CloudTrail records every call

    Each IAM-checked call, allowed or refused, is logged with the principal that made it. That's how the first deploy's refused sign-in was diagnosed: the log showed exactly which subject GitHub sent.

    Claude through Bedrock

    The task role's invoke-claude policy has two parts. It allows bedrock:InvokeModel on our two US inference profiles. A profile forwards the call to the model in another US region, so it also allows the foundation models in any region, but only when the call came through one of our profiles (condition bedrock:InferenceProfileArn). Checked with the IAM policy simulator: via the profile allowed, direct call denied, other models denied. No API key is involved, so every credential on AWS is a short-lived IAM one. Trade-off: Anthropic's server-side model fallback isn't available on Bedrock.

    What the first deploy taught us

    GitHub's identity format

    GitHub sends repo:jchandel8@191924894/AdvisorAgent@1452303973:environment:demo, with permanent IDs. The role trusted the name only, so AWS refused. Found by reading the refused sign-in in CloudTrail.

    A required log setting

    ECS rejected the service without log_stream_prefix, although the Terraform provider marks it optional. terraform validate can't catch API rules like this.

    A provider bug that taints

    AWS filled in autoscaling defaults, the provider called it an error and marked the service tainted. Setting the values explicitly and running terraform untaint kept the healthy service and its URL.

    Listed is not enabled

    Bedrock listed Sonnet 5.5 and Haiku 5.5 as authorized, but calling them returned "not available for this account". A one-token test of each model found the newest that works (Sonnet 4.6, Haiku 4.5), and Haiku 4.5 needed one request field dropped (effort). Always test the real call before deploying.

    A URL that moves

    Each re-created Express service gets a new URL. The deploy now updates Cognito's allow-list itself, reading and re-sending the full client settings, because the update call resets anything not sent.

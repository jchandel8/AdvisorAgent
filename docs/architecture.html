AdvisorAgent architecture

Three web portals (advisor, client, admin) and one AI assistant share a single backend. People sign in with Amazon Cognito; the backend reads who you are only from the verified token. Everything an advisor or client sees, including every lookup the AI makes, goes through one access layer that reads only accounts the signed-in person has an account_access row for. The AI agent (ochre) lives inside the backend: it asks for data through six read-only tools, never sees who it acts for, and never touches the database directly. Admins change who can see what; every change is written to an audit log in the same transaction. Documents are shared per account: anyone with access to an account (its advisors and its owners) sees, opens and downloads its documents. Files sit in a private S3 bucket and are streamed through the backend after the same access check, and every open is recorded.

    How it runs on AWS

    The AI agent

    What it is and what it does

    The advisor's "Advanced Assistant". It turns a plain-English question into a few precise lookups, reads the results and writes an answer. It runs inside the FastAPI backend, uses Claude (the Anthropic API locally, Amazon Bedrock on AWS; one setting, same code), and reaches data only through tools the backend defines. It is a manual tool-use loop, so every step is code you can read in backend/src/wealth/agent/loop.py.

    How one question is answered

    1. Limits are checked and the request is logged.
    2. Haiku 5.5 checks the question is about the advisor's clients.
    3. Sonnet 5.5 gets the question and the tool list (no advisor_id in it).
    4. Sonnet asks for tools; the backend runs each one as the signed-in advisor.
    5. Results go back; Sonnet repeats (up to 10 rounds) or answers.
    6. The answer is checked, cached, and saved with the conversation.

    Its six tools

    • get_my_clients: clients the advisor shares an account with
    • get_accounts: one client's shared accounts
    • get_holdings: positions, sector and asset-class mix, with filters
    • get_transactions: activity and realized gains, with filters
    • get_performance: returns from 1 day to 5 years
    • find_reviews_due: reviews due soon or overdue

    All math (totals, weights, gains) is done in SQL, not by the model.

    Guardrails

    • Limits: 10 a minute and 100 a day per advisor.
    • Scope check: off-topic and manipulation are blocked before Sonnet runs; fails closed.
    • Facts only: no buy or sell recommendations.
    • Selected client: a hard scope in the access layer.
    • Answer check: figures must come from looked-up data.
    • Audit log: every request, with its outcome, shown in the admin portal.

    What it can never do

    • Choose or change who it acts for. The advisor comes from the verified Cognito token.
    • Write SQL or touch the database. It only calls the six tools.
    • Change data. Tools run in read-only transactions.
    • See accounts without an account_access row. Unknown and forbidden IDs look identical.

    The three portals

    Client portal

    Dashboard, holdings, transactions and gains, performance, documents, profile. Only the client's own accounts; joint accounts appear for both owners.

    Advisor portal

    Client book, a client's shared accounts, the AI assistant, documents, profile. Only accounts the advisor has an access row for.

    Admin portal

    Create users (database row and Cognito login together), create accounts, grant and revoke access, drill into any user or account, read documents (every open audited), and read the audit log and the assistant log. Admins manage access; they don't read portfolios.

    Access layer

    One SQL fragment, VISIBLE, decides which accounts a person can see. Every portal query, every document query and every agent tool starts with WITH visible AS (...) and joins through it.

    RuleHow it is enforced
    Only accounts you are onAn account_access row for this advisor or client, matched by advisor_id or client_id (never by name).
    Only open accountsaccounts.close_date IS NULL. Closing an account hides it, and its documents, everywhere.
    Shared accounts onlyAn advisor sees a client only through accounts they share, so a client's other accounts never appear.
    Selected client in the assistantfocus_client_id narrows visible to that client's accounts. It is a hard filter in SQL, not a hint in the prompt, and it is checked again before every tool call.
    No ID probingAn unknown ID and a forbidden ID get the same answer (404, or “not found” for tools).
    Changes apply at onceNothing is cached per person, so a grant or revoke shows on the next request.

    Where: backend/src/wealth/access.py; read-only transactions in backend/src/wealth/db.py.

    Document sharing

    A document always belongs to one account. Everyone with access to that account sees it, so an advisor and a client, or two joint owners, can share files for each other to review. Seeded documents (statements, policy statements, review notes) keep their text in the database; uploaded files go to S3.

    Rule or stepDetail
    Who sees a documentAnyone the access layer shows the account to: its advisors and its clients, on open accounts. A shared-one-account advisor never sees documents on the client's other accounts. Revoking access hides them on the next request.
    Who may uploadAdvisors and clients with a non-viewer access row on an open account. The account is a required field, and the list offers only those accounts. Admins don't upload.
    File checksAt most 10 MB (413 if larger). Extension on an allow-list: PDF, TXT, PNG, JPG/JPEG, DOCX. The content must match: PDF and image signatures, valid UTF-8 text, a DOCX that is a real Word zip. Otherwise 422. The filename is cleaned before it is stored.
    SavingOne transaction: the documents row (uploader, size, SHA-256, content type, original name, note) and an upload event. Then the file goes to documents/{account_id}/{random UUID}. If S3 fails, the request returns 502 and the transaction rolls back, so nothing half-saved remains.
    Opening and downloadingThe access check runs again, then the backend reads the file and streams it. There are no public or pre-signed S3 links. Headers: Cache-Control: no-store, X-Content-Type-Options: nosniff, Content-Security-Policy: sandbox, and a cleaned filename.
    New, menu count, opened byFrom document_events. A document is New for you if someone else uploaded it and you haven't opened or downloaded it. “Opened by” lists the other people who have. Seeded documents are never New.
    DeletingOnly the uploader, with a confirm step. Sets deleted_at, so it disappears for everyone, but the row, the file and the history stay for the audit. Admins still see it, marked deleted.
    AdminsSee every document and who opened it, across all three portals. They can preview text and download any file. Each preview or download writes a permission_audit row in the same transaction.
    Storage locallyAn s3 container (adobe/s3mock, S3-compatible) with the bucket created at start. The same boto3 code runs against it.
    Storage on AWSBucket advisoragent-documents-<account id>: all public access blocked, owner-enforced, AES-256 encryption, a policy that denies non-HTTPS requests. The task role may only s3:PutObject and s3:GetObject under documents/* (no list, no delete). Teardown deletes the bucket and its files.

    Where: backend/src/wealth/api/routes_documents.py, backend/src/wealth/storage.py, migrations 006 and 007, frontend/src/app/pages/documents.ts, infra/app/main.tf.

    Data model

    Postgres 17. Snake case, integer keys, a foreign key for every link, money as numeric. Market value, client counts, weights and gains are computed in SQL, not stored. Seven migrations, applied in order at start.

    TableHolds
    advisors, clients, adminsPeople. Usernames match Cognito. No passwords anywhere in the database.
    accountsIndividual, joint, IRA or trust; open and close dates.
    account_accessThe ACL: one row links an account to one advisor or client with a role (owner, joint owner, advisor, viewer). Checks enforce exactly one person and a role that fits.
    securities, asset_classes, sectors, currenciesReference data for about 60 real tickers.
    holdings, transactions, performanceMonth-end positions, 2 years of activity, monthly returns from 1 day to 5 years.
    documentsSeeded text or uploaded file details (storage key, type, size, SHA-256, uploader, note, deleted_at). Checks: at most one uploader (an advisor or a client), and either text or a file.
    document_eventsUpload, view, download and delete, by which advisor or client, and when.
    permission_auditThe admin audit log.
    agent_conversations, answer_cache, assistant_eventsAssistant chat history, cached answers, and the request log used for limits.
    demo_usersWhich seeded people are the demo users, and what each can see.

    Trade-offs and known limits

    • Files are streamed through the API, not by pre-signed S3 links. That means one code path locally and on AWS and no public bucket address; the 10 MB limit keeps memory use small.
    • The file is written to S3 before the database transaction commits. If the commit then fails, an unreferenced file stays in the bucket. No one can reach it, and teardown removes it.
    • Uploaded files aren't virus-scanned. Content checks stop disguised files, and the sandbox header stops them from running scripts in the browser.
    • Deleting a document hides it but keeps the file, for the audit. A real firm would add a retention policy.
    • One task and a single-zone database keep the demo near $0.10–0.15 an hour; production would run at least two tasks across availability zones.

AdvisorAgent architecture

Three web portals (advisor, client, admin) and one AI assistant share a single backend. People sign in with Amazon Cognito; the backend reads who you are only from the verified token. Everything an advisor or client sees, including every lookup the AI makes, goes through one access layer that reads only accounts the signed-in person has an account_access row for. The AI agent (ochre) lives inside the backend: it asks for data through six read-only tools, never sees who it acts for, and never touches the database directly. Admins change who can see what; every change is written to an audit log in the same transaction.

    How it runs on AWS

    The AI agent

    What it is and what it does

    The advisor's "Advanced Assistant". It turns a plain-English question into a few precise lookups, reads the results and writes an answer. It runs inside the FastAPI backend, uses Claude (the Anthropic API locally, Amazon Bedrock on AWS; one setting, same code), and reaches data only through tools the backend defines. It is a manual tool-use loop, so every step is code you can read in backend/src/wealth/agent/loop.py.

    How one question is answered

    1. Limits are checked and the request is logged.
    2. Haiku 5.5 checks the question is about the advisor's clients.
    3. Sonnet 5.5 gets the question and the tool list (no advisor_id in it).
    4. Sonnet asks for tools; the backend runs each one as the signed-in advisor.
    5. Results go back; Sonnet repeats (up to 10 rounds) or answers.
    6. The answer is checked, cached, and saved with the conversation.

    Its six tools

    • get_my_clients: clients the advisor shares an account with
    • get_accounts: one client's shared accounts
    • get_holdings: positions, sector and asset-class mix, with filters
    • get_transactions: activity and realized gains, with filters
    • get_performance: returns from 1 day to 5 years
    • find_reviews_due: reviews due soon or overdue

    All math (totals, weights, gains) is done in SQL, not by the model.

    Guardrails

    • Limits: 10 a minute and 100 a day per advisor.
    • Scope check: off-topic and manipulation are blocked before Sonnet runs; fails closed.
    • Facts only: no buy or sell recommendations.
    • Selected client: a hard scope in the access layer.
    • Answer check: figures must come from looked-up data.
    • Audit log: every request, with its outcome, shown in the admin portal.

    What it can never do

    • Choose or change who it acts for. The advisor comes from the verified Cognito token.
    • Write SQL or touch the database. It only calls the six tools.
    • Change data. Tools run in read-only transactions.
    • See accounts without an account_access row. Unknown and forbidden IDs look identical.

    The three portals

    Client portal

    Dashboard, holdings, transactions and gains, performance, profile. Only the client's own accounts; joint accounts appear for both owners.

    Advisor portal

    Client book, a client's shared accounts, the AI assistant, profile. Only accounts the advisor has an access row for.

    Admin portal

    Create users (database row and Cognito login together), create accounts, grant and revoke access, read the audit log and the assistant log. Admins manage access; they don't read portfolios.
